# Opening a PR

Invoked at the end of every other playbook that changes code. `scripts/ai/pr.sh` opens the PR, and `/verify`'s report is its body.

1. **Work from your own checkout.** A worktree off the default branch (`scripts/ai/worktree.sh new <name>`, `claude --worktree <name>`, or an Agent with `isolation: "worktree"`) gives the work its own simulator and DerivedData. Two agents on the same branch each get their own worktree. A dirty branch with someone else's work stays theirs. Stage only your files, by path. A snarled worktree is reset from the default branch and redone minimally. **Check.** `git status --short` lists only files you mean to ship, or files you will leave alone and can name.
2. **Commit in small, ordered steps.** Commit liberally while working, then shape the history into small ordered commits before opening the PR. Each commit is landable and tells the next part of the story. Amend when the fix belongs in the commit you just made. Make a new commit when it is separable. A bug fix commits the failing check before the fix. **Check.** `git log --oneline origin/<default branch>..HEAD` reads as a story.
3. **Clean the diff.** Run `/unslop` and `/no-comments` over the diff. Write every PR title, description and commit body with `/technical-writing`, then `/unslop`. Apply every technical-writing layer except Diátaxis. Use one word for each action, keep articles, prefer a plain verb to an `-ing` form. **Check.** The diff holds no narrating comments and no dead code.
4. **Gate it.** Run `/verify`, with `VERIFY_INTENT="<what the change should make visible>"` so the AI judge knows what to look for. `scripts/ai/verify.sh` writes `.build/verify/report.md` with the gate table and the visual verdict from the AI judge (`scripts/ai/judge.py`), or from you through `python3 scripts/ai/history.py judge` when `VISUAL_JUDGE=human`. Fill its **Not verified here** list. **Check.** `python3 scripts/ai/history.py verified` exits 0 on HEAD, or each failing gate is explained in the report.
5. **Title it.** Conventional Commits, `type(scope): subject`. Type is `feat`, `fix`, `docs`, `refactor`, `test`, `chore` or `perf`. Scope is the changed area, such as `capture`, `sync` or `ios-loop`. The subject is short and imperative, names a real symbol when one carries the change, and has no trailing period. For example, `fix(capture): keep RambleView's submit button above the keyboard`. **Check.** The title fits on one line and names the change, not the activity.
6. **Open it.** `scripts/ai/pr.sh --title "<title>"`. On the default branch it moves your commits to a new branch first and puts the default branch back on origin's tip. Then it pushes and opens the PR against the default branch, ready, with `/verify`'s report as the body when the report is fresh for this commit. `--draft` only marks work that stopped on a failing gate, as `/ship` does after three attempts. A stack child then targets its parent with `gh pr edit <n> --base <parent-branch>`. The root of a stack targets the default branch. Prefer five narrow PRs to one large one. **Check.** `gh pr view <n> --json isDraft,baseRefName,url` shows a ready PR on the right base.
7. **Write the briefing above the report.** The PR body is a briefing, not the lab notebook. A reviewer with the diff learns why the change exists, what it leaves out, what it could break and how it was proven, in under a minute. Short, simple sentences with few identifiers. Use these `##` sections in order and drop any that has nothing to say.
   - `## Why` gives the problem and the approach in one to three sentences.
   - `## What changed` has one to three bullets. Name a real symbol or path only when it carries the change. Name both sides of a rename.
   - `## Scope` names what the PR covers and what it deliberately leaves out, in one to three items.
   - `## Tradeoffs` names only rejected alternatives a reviewer would otherwise ask about.
   - `## Blast Radius` gives one or two sentences on which screens, data or users the change reaches (`python3 scripts/ai/blast-radius.py <files>`) and why that is safe or risky.
   - `## Verification` is `/verify`'s report, unchanged, with its gate table, its visual verdict and its **Not verified here** list. For a performance change, add one primary number with its unit as `before → after` and the device it ran on.

   Write the briefing to a file, append `.build/verify/report.md` unchanged (its first line is the kit's marker), and set it with `gh pr edit <n> --body-file <file>`. A later `pr.sh` run after a fresh `/verify` replaces a marked body with the new report alone, so re-add the briefing then. Attach screenshots or a recording when they prove a claim. Never paste full SHAs, lane recitals, file-by-file checklists or "CLEAN" verdicts into the body. The squash commit body is the PR body, so keep it under about 40 lines. **Check.** `gh pr view <n> --json body` shows the briefing and a report stamped with the current head SHA.
8. **Post the link and keep building.** Opening a PR does not start a babysit. Finish the phase or the stack first. `/lead` tracks the PR to merged. A babysit runs only when the owner asks for one after the whole stack exists (`playbooks/babysit.md`). Push back when feedback drifts from the intent. **Check.** The reply carries the PR link.

A subagent that opens a PR runs `/interrogate`, `/unslop` and `/no-comments`, posts the link, and returns to its parent without babysitting, unless it is an Autopilot-full or Autopilot-stack owner. That owner's brief assigns the babysit loop and is the ask `playbooks/babysit.md` waits for. The owner starts the loop after its code-ready report and reports merge-ready or STACK-READY as its playbook says.

**Reply:** the PR link as `https://github.com/<owner>/<repo>/pull/<number>`, its title, the gate table result, and the **Not verified here** list.
