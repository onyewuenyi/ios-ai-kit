# Autopilot-stack

**You own the stack, never the landing. Build and verify the queue with full autonomy, then hand the operator one linear base-branch stack to review and land.** The sibling of `playbooks/autopilot-full.md`.

1. **Run the owner loop of Autopilot-full, minus the merge.** One fresh local owner per PR (Agent tool, `isolation: "worktree"`, `run_in_background: true`) runs `/ship` up to an open, babysat PR and stops there. Its brief forbids `scripts/ai/merge.sh`. Everything else in Autopilot-full step 2 holds. The early trail and first push within about 15 minutes, the PR opened ready with `scripts/ai/pr.sh`, `/verify` with the AI judge, review triage per `../references/review-triage.md`, `/unslop` and `/no-comments`, babysit to green per `playbooks/babysit.md`, and the `children.tsv`. Owners run in parallel when the work is self-contained. **Check.** Every owner has a pushed branch, a ready PR and a trail.
2. **Audit on a real loop.** Run the hourly tick of Autopilot-full step 6. On the operator's go, arm `/loop 1h`. At each tick, re-read this playbook from trunk (`git show origin/main:.claude/skills/ios-loop/playbooks/autopilot-stack.md`), audit the operation against it and fix drift in that tick. Count only side effects as progress. Stand down a stuck lane and dispatch its replacement at once. **Check.** The tick's row in your trail names what changed, or says none.
3. **Hold the operator gates.** State-then-wait, so a request to state the plan is not a go. On the operator's stop, every owner takes an immediate zero-writes hold. **Check.** The go is on record before the first spawn.
4. **Verify each round.** The owner reports its code-ready head SHA once the shipped code is final, and STACK-READY with the exact head SHA when its loop is green. You verify each round per Autopilot-full step 4, with STACK-READY in place of merge-ready. Nothing enters the stack unverified. **Check.** Each STACK-READY head has a clean verdict naming that SHA.
5. **Append on a clean verdict, never ship.** No owner merges, arms auto-merge or closes. A clean verdict appends the PR to the one linear base-branch stack, in verified order or an order the operator specified. **Check.** `gh pr list --json number,baseRefName` shows exactly one chain, with only its root targeting the default branch.
6. **Single writer on topology, parallel writers on builds.** Owners push only their own branches and report the tip, the current base and the intended parent. You are the only topology writer. To append a PR, fetch the intended parent, merge the parent's exact tip into the child branch (`git merge origin/<parent-branch>` in the child's worktree), push it with `scripts/ai/pr.sh`, and set the PR's base with `gh pr edit <n> --base <parent-branch>`. Never rebase and never force-push. **Check.** Each child's head contains its parent's tip, from `git merge-base --is-ancestor origin/<parent-branch> origin/<child-branch>`.
7. **Absorb drift at the root, then re-verify what moved.** Fetch the default branch and merge it into the root of the chain, then each parent into its child, bottom to top. When a merge surfaces conflicts in an owner's files, that owner fixes its own slice and you push the result. Every new head voids the verify history at the old SHA. Apply the patch-id rule in `playbooks/shipping.md` at each verdict SHA. A link whose patch changed goes back through step 4 before delivery. Re-run `/verify` at every new head even when the patch-id is unchanged, so `python3 scripts/ai/prs.py --check <n>` reads verified. A genuinely new raise of a pinned value still needs your fresh countersign. Absorbing landed values is not a raise. **Check.** Every link reads verified at its current head.
8. **Deliver the chain.** One linear chain of verified PRs, reviewable bottom-up on GitHub, each carrying its verdict and its `/verify` report in the PR body or a comment. The operator reviews and lands it bottom-up, by hand or with `scripts/ai/merge.sh <n> --yes` per `playbooks/shipping.md`. **Check.** Every link's PR body or comment names its verdict and head SHA.

**Choosing between the autopilots.** Autopilot-full when the PRs are independent and landing authority is granted. Autopilot-stack when the operator wants review before landing, the work is sequenced or coupled, or merge authority is withheld.

**Reply:** links to the stack root and tip, a one-line verdict summary per link, and anything parked or excluded with the reason.
