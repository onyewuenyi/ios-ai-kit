# Hillclimb

**You own the metric and the experiment's integrity. Supervise and review. Delegate the attempts.**

Sustained, scientific improvement of one measurable thing against a target, over many attempts. An eval score, a model's latency or accuracy, a false-accept rate, a segmentation rate, launch time, a view's cost at scale. Used heavily for on-device AI (Foundation Models) and cloud-model features. A one-off fix is `playbooks/bug-fix.md` or `playbooks/perf.md`. This is the loop.

Core discipline is one change, one measurement, keep or revert. Never stack untested changes, and never claim a win from code inspection (principle-prove-it-works).

1. **Ground the workload, then fix the metric.** Run `/how` over the target. Name the realistic workload dimensions that can move the result (store size, history length, corpus mix, text size, device class, concurrency) and pick a case that reproduces the user's complaint. If no case reproduces it, fix the repro instead of hillclimbing. Then name the metric, the direction that counts as better, the corpus, and the gate (the critical error that must never rise, such as a false accept). Write a stop predicate that pairs a target with a floor on attempts, so a lucky early win cannot end the run ("at least 50% better than baseline and at least 10 iterations"). Use the user's numbers when given. **Check.** Metric, direction, corpus, gate and predicate are one block in the todo list.
2. **Stamp every run.** App build or commit, OS version AND build (the on-device model's only version fingerprint), device or `sim:` prefix, model id, configuration fingerprint, time. A number without its stamp cannot be compared with anything. **Check.** The harness prints the stamp on every run.
3. **Build the harness, prove it, then freeze it** (principle-build-the-lever). One repeatable command emits the metric, sampled enough to clear the noise (median of N, not one run). It prints its error count and a count of the work done. Prove its sensitivity with contrasting workloads. The target case shows the symptom and easier cases separate as expected. Bracket the metric with a case it must score as right and one it must score as wrong (principle-explain-the-number). Prove the harness answered. If fewer than about 90% of cases were served by the arm under test, the run is DEGRADED, and you report the error, not the score. Vet it with `/benchmark-checklist`. If the harness cannot distinguish the cases, revise the workload or the metric. **Check.** Both bracket cases score correctly, the served share is printed, and the harness is committed or frozen at a named path.
4. **Baseline** on the unchanged code, the same corpus, the same device class. Record a green run of the regression gate (the tests that must keep passing, `scripts/ai/test.sh`) beside it. **Check.** The baseline row and the green gate are in the log before any change.
5. **Open the decision log** with `/show-me-your-work`. A `decision.tsv` outside the tree (under `.build/`, gitignored), one row per attempt: id, hypothesis, change, before, after, delta, gate, tests, verdict (kept or reverted), stamp, note. Read it before each attempt. **Check.** The file exists with its header and the baseline row.
6. **Ground each hypothesis in a mechanism** from step 1 ("move the store fetch off the launch path because it blocks first frame"), not "try caching something". For a performance metric, order hypotheses by the mantras in `playbooks/perf.md` step 5. Borrow only their order, not that step's stop rule. **Check.** The next hypothesis names its mechanism.
7. **Loop, one hypothesis per iteration.**
   - Hand the change to an `ios-agent` subagent (model from `MODEL_CODE` in `.claude/ios.env`, `sonnet` by default) with a tight scope. Supervise and review the diff rather than typing it (principle-guard-the-context-window). When several independent hypotheses are live, fan them out, each in its own worktree (`scripts/ai/worktree.sh new <name>`), so builds and simulators never collide (principle-separate-before-serializing-shared-state).
   - Measure before and after with the frozen harness, on the same device class, and run the regression gate. Repeat a model run for variance.
   - Accept only when the metric moves past noise AND the gate holds AND the tests stay green. Otherwise revert the change in full. A tweak that "might help" is not kept.
   - A defect found by eye becomes a labelled corpus case before it is fixed, so the number sees it.
   - One commit per accepted win, staged by path (never `git add -A`), with the before and after numbers in the message. Log the row either way.
   - If the run is unattended, borrow only the pacing from `playbooks/autonomous.md`, not its stop rule.

   **Check.** Each iteration ends with a logged row before the next begins (principle-sequence-verifiable-units).
8. **Push past the first plateau.** On a stall or several rejects in a row, pivot category, combine near-misses, re-read the source, or try something more radical before concluding the hill is climbed. Correctness and simplicity outrank the number. Revert a win that breaks behavior, and keep a simplification that holds the number (principle-laziness-protocol). **Check.** At least one different category was tried after the first stall.
9. **Stop on the predicate,** or when the remaining ideas are marginal and not worth their cost. Do not relax the predicate to meet it, and do not quit while cheap untried hypotheses remain. Move floors and thresholds only in the direction the observed numbers support. If you are stuck, surface it instead of spinning. **Check.** The final row meets the predicate, or the reply says which part did not and why.
10. **Run `/verify`, then the Opening a PR playbook** (`playbooks/opening-a-pr.md`, `scripts/ai/pr.sh`) with the accepted commits stacked in the order they landed. `/verify` runs the gates and the AI judge on the visual sheets, recorded by `scripts/ai/history.py judge`. **Check.** Every gate passes and the PR link exists.

**Reply:** the metric and target; baseline to final with the percent delta; a trajectory table with the gate's value at each step; iterations run (kept vs reverted) and why each revert happened; each accepted fix on one line; the `decision.tsv` path; the stamp of the final run; the best idea you would try next if pushed further; the PR link.
