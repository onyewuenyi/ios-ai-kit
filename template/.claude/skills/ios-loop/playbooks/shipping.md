# Shipping

**You own what lands. Verify each PR independently, land only the verified run from the bottom, then keep your hands off the queue.** This is the half after `playbooks/babysit.md`. It runs only on an explicit request to merge, land or ship. Merging is never implied by anything else (Autonomy, in the `ios-loop` skill). One idea taken all the way to merged is `/ship`, which ends in this playbook's landing steps.

1. **Freeze the run.** List the PRs bottom to top. A stack is a base-branch chain whose root targets the default branch. Independent PRs are each a run of one and ship on their own. **Check.** The list is written down with each PR's base branch, from `gh pr view <n> --json baseRefName,headRefName,headRefOid`.
2. **Verify every PR independently.** One fresh subagent per PR, never batched, never the agent that wrote the code. Each works in `scripts/ai/worktree.sh pr <n>` on its own simulator.
   - It runs `scripts/ai/verify.sh`. The AI judge (`scripts/ai/judge.py`) records the visual verdict through `history.py judge` unless `VISUAL_JUDGE=human`, in which case the subagent judges the sheets with `ui-verify` and records the verdict itself.
   - It exercises the load-bearing behavior on the simulator, parent against head. It drives the same seam (`scripts/ai/sim.sh launch <args>`) or deep link (`scripts/ai/sim.sh openurl <url>`) at the parent and at the head and asserts the hierarchy with `scripts/ai/xcui.py` or the `ui-verify` agent. It lays the two screenshots side by side with `scripts/ai/sim.sh compare <out.png> parent=<a.png> head=<b.png>`.
   - It returns `PASS`, `PASS+NOTES` or `FAIL` with the head SHA and the evidence paths.

   Safe means a verdict from an agent that did not write the code. CI green is not a verdict, an approving bot review is not a verdict, and a cloud session's self-report is not a verdict (cloud sessions have no Xcode). Post each verdict on its own PR with `gh pr comment <n> --body-file <verdict.md>` when `LEAD_COMMENT=1` or the owner said yes this session. Otherwise it lives in the report. **Check.** Every PR in the list has a verdict at its current head SHA, and `python3 scripts/ai/history.py verified <sha>` exits 0 for each PASS.
3. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without a passing verdict. `PASS` and `PASS+NOTES` both pass. A verified PR above an unverified one is not landable. **Check.** The ceiling is named as a PR number, with what breaks the chain above it.
4. **Re-check that each verdict still describes the patch.** Record each verdict's head SHA, base SHA and patch-id (`git diff $(git merge-base origin/<base> <head>) <head> | git patch-id --stable`). A merge of the base or a retarget changes the head SHA. The verify history is keyed by SHA, so `merge.sh` will refuse the new head until it is verified again. When the patch-id is unchanged, re-run `scripts/ai/verify.sh` at the new head and keep the behavior verdict of step 2. When the patch-id changed, step 2 runs again in full. Never accept matching commit messages, or a green check from an older SHA, as a substitute. **Check.** For each PR about to land, the recorded patch-id matches the current one, or a fresh step 2 verdict exists.
5. **Prepare only the bottom PR.** Fetch. If the bottom PR targets a merged parent, retarget it with `gh pr edit <n> --base <default branch>`. If it is behind the default branch, merge it in (`git merge origin/<default branch>` in its worktree), push with `scripts/ai/pr.sh`, and run step 4 again. Never rebase, force-push, retarget or merge a descendant yet. **Check.** `gh pr view <n> --json baseRefName,mergeable` shows the default branch and `MERGEABLE`.
6. **Land one PR at a time.** `scripts/ai/merge.sh <n> --yes`. It merges only when `python3 scripts/ai/prs.py --check <n>` says merge-ready (verified at its head, visual judged, mergeable, checks green, no open threads), deletes the branch, and syncs the local default branch. Add `--wait <seconds>` when checks are still running. It refuses in a cloud session. Do not call `gh pr merge` or arm GitHub auto-merge around it. **Check.** `merge.sh` exits 0, and `gh pr view <n> --json state,mergedAt` shows `MERGED`.
7. **Recompute after every merge.** Fetch, confirm the merge commit is on `origin/<default branch>`, drop the merged PR from the frozen list, and inspect the new bottom PR's base, head, checks and patch-id. GitHub may retarget a child when its parent branch is deleted. Do not assume it did. Repeat steps 4 to 6 for that one PR. Independent work stays outside this chain. **Check.** The new bottom's base and head SHA are read from `gh`, not assumed.
8. **Do not mutate the queue while a merge is pending.** `merge.sh --wait` holds the watch. When it times out, re-read `python3 scripts/ai/prs.py --check <n>` and diagnose before touching anything. A required check that failed, a `CONFLICTING` state or a closed PR with no merge is a hard stop. Checks still pending is not a failure. Hold longer waits under `/loop` in dynamic mode. **Check.** Each merge and each new ceiling is reported as it happens.
9. **Stop at the ceiling.** When the verified run is merged, `scripts/ai/worktree.sh prune` returns the merged PRs' worktrees and simulators. Report what landed, which PR is the next unverified one, and what verifying it would take. Extending the run is a new pass through step 2. **Check.** Every PR in the frozen list is merged, or named as above the ceiling with its reason.

**Reply:** the verified run and its ceiling, each PR's verdict and which agent produced it, what landed with `merge.sh`, the patch-id checks, and what the next gap needs.
